# 写一份别人能接着做的交接文档

接手的人打开文档，应该能直接回答三个问题：工作停在哪里，第一步做什么，看到什么结果才算完成。先看接手者接下来要做什么，再选一种写法。

## 选一种交接方式

| 场景 | 怎么写 | 交给对方什么 |
| --- | --- | --- |
| 同一台设备换一个 Agent，下一项任务已经明确 | 客户端有 Matt Pocock 的 `handoff` 时，用它写一份围绕下次任务的短简报。计划、决定和 diff 直接给链接，注明接手时值得用的技能及用途 | 一份临时 Markdown 的路径。上游默认写到系统临时目录，使用时遵守宿主的临时文件约定 |
| 长任务暂停，有未提交工作、关键取舍，或要接着上次的记录继续 | 客户端有 Softaworks 的 `session-handoff` 时，用它创建或接续记录。创建时核对脚本采集的 Git 状态，补上决策依据和第一步；恢复时先检查记录是否过期，再对照当前仓库 | 一份交接记录的路径。上游脚本默认写入项目的 `.claude/handoffs/`，适合项目接受该目录时使用 |
| 给人交接、换设备，或项目已有指定记录位置 | 在接手者能访问的任务单、PR 或交接页更新下方提纲。即使同时换 Agent，也优先用这个已有入口。几行能写清的小任务就写几行 | 可访问的链接，或已交付的仓库相对路径和版本。接手者应能在自己的环境打开它 |

在 Codex 里可以直接点名技能。例如：“用 `$handoff` 给下一轮写个短简报，下一轮只复测播放器关闭后是否停住。”恢复长任务时可以说：“用 `$session-handoff` 读取这份交接，先核对分支和未提交改动，再做第一项待办。”过期检查读取本地状态；如果下一步取决于 PR 是否已合并或网站是否已上线，还要打开对应的 PR 或正式网址核实。

两种技能都可单独使用。当前客户端缺少对应技能，或其默认落盘位置不适合接收方时，直接在约定位置用下面的提纲写；全过程维护一份可接续的记录。短简报交给下一位 Agent 并确认取到后，可按项目约定清理。长任务恢复时，分支、提交和未提交改动以接手时的实际状态为准。[Matt Pocock 的 handoff](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/productivity/handoff/SKILL.md) · [Softaworks 的 session-handoff](https://github.com/softaworks/agent-toolkit/blob/3027f20f3181758385a1bb8c022d4041dfb4de84/skills/session-handoff/SKILL.md)

## 动笔前

先确认谁接手、对方能访问哪些材料、能执行哪些操作。写给同事，用对方熟悉的业务场景开头。写给新 Agent，把目标、第一步和验收条件写成可以直接执行的一段话。跨设备时，用仓库相对路径和版本定位材料，单独标出还只在原设备上的修改。公开协作只放可公开核实的事实，凭据由接手者通过自己的授权渠道取得。[文件与设备](files-and-devices.md)

## 可直接填写的提纲

用任务名作标题，按接手者动手的顺序写。按需删去空项。

```markdown
# 接手〈任务名〉

〈接手人或角色〉下一步要完成〈可观察的结果〉。现在停在〈具体步骤〉。

## 从这里开始

截至〈日期，必要时写时区〉，工作在〈仓库 / 分支 / 提交，或文档及修订版〉。
打开〈入口〉，先做〈操作或命令，注明工作目录和必要条件〉。应当看到〈结果〉。

## 已经确认的事

- 〈已完成的事〉。在〈版本和环境〉执行〈检查〉，观察到〈结果〉。〈证据位置〉
- 〈影响下一步的决定〉。因为〈约束或取舍〉，选择了〈方案〉。

## 接下来

- 〈谁〉做〈下一步〉，用〈可观察的结果〉验收，并把结果记到〈位置〉。
- 〈待确认的问题〉由〈能决定的角色〉根据〈所需材料〉决定。等待期间可以先做〈独立事项〉。
- 接手者可以执行〈已确认的范围〉。到〈需要另行授权的动作〉前停下。
```

写“已完成”时，区分本地检查、CI、合并、部署和实际使用，只列与这次交接有关的层级。失败过的尝试如果会影响下一步，写清触发条件、看到的结果和仍然未知的部分。若有未提交修改、唯一素材、后台任务或临时目录，写明归谁、在哪里、为什么保留、满足什么条件才可清理。把已有计划、PR 和日志链接到具体位置，避免在多份文档里维护同一份待办。

## 示例：把播放器问题交给下一位维护者

下面还原的是此项目在 PR #7 合并后、PR #8 修复前的交接。问题后来已经关闭。[试写页与录屏](https://github.com/tangyixiao/tangyixiao-workflow/pull/7) · [后续修复与验证](https://github.com/tangyixiao/tangyixiao-workflow/pull/8)

> 下一位维护者请查一下：快速关掉录像后，播放进度为什么还在走。在仓库根目录运行 `git show 7703ea9:project-website/templates/workbench.js`，可以看到这个版本在弹窗的 `close` 事件里暂停录像。复现时使用这个版本。
>
> 在提交 `7703ea9` 的检出目录，用 Chrome 打开 `project-website/site/index.html`。打开录像，点画面暂停。再点画面继续播放，马上关掉弹窗。线上曾观察到弹窗已关，进度仍从 34.70 秒走到 38.67 秒。普通播放时点关闭可以停住。已有浏览器检查只观察了刚关闭的那一刻。
>
> 先复现这组操作并记下进度，再修改播放器。复测时，在浏览器控制台读取 `document.querySelector('#terminal-video').currentTime`，关闭后一秒再读一次，应当停稳。重新打开，应当从原位置继续。把修复前后的观察结果放进修复 PR，交给维护者评审。

## 接手和回写

接手者先打开交接里给的入口，核对当前版本、未提交改动、PR 状态或任务负责人。示例里的旧提交适合查历史；实际接手时若修复已经合并，就从现状核对验收结果。跑得通的第一步和找得到的证据，比填满所有栏目更能说明文档可用。发现版本变了、链接失效或阻塞已经解除，就把新事实和下一步写回同一份记录。有决定会改变范围、访问权限或公开程度时，再请能决定的人确认。[计划与决策](planning-and-decisions.md)
