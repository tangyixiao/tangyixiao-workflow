# 复用现有实现、选择技术栈与管理任务分支

## 先找已有能力

1. 从用户实际调用的入口查起。搜索仓库已有功能、配置、脚本、测试、开放中的 PR，以及维护者近期合并的同类改动。确认现有实现能否直接满足需求，进行中的贡献能否接着做。一个配置项就能解决的问题，到这里即可结束查找。
2. 仓库内仍有缺口时，核对标准库、当前锁定版本的依赖和平台原生能力。需要新依赖时，再查官方文档、上游实现和仍在维护的同类项目。用任务里的一个实际输入或使用场景核验关键行为，检查版本兼容、维护状态、许可证和署名义务、所需权限、安全更新，以及引入和升级的成本。
3. 已有接口满足要求就直接采用。接口或数据格式有小差异时，用薄适配层衔接。只有现有方案有具体缺口时才自行实现，并只实现缺失的部分。影响依赖、兼容性或长期维护的选择，在现有 PR 或设计记录中用一两句写明比较过的方案、缺口和取舍。

工作方法也可复用。项目采用 GitHub Flow 时，沿用其分支与 PR 流程。已经使用 Superpowers 的项目可调用与当前任务匹配的技能，无需在仓库内复制整套流程。[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) · [Superpowers](https://github.com/obra/superpowers)

## 选择技术栈

先写清谁会在什么环境里做哪件事，以及怎样算成功。例如，要把工具发给一台离线 Windows 电脑，就先确认对方能否安装运行时、能拿到什么安装包、拿到后能否直接处理一份样本。用这些条件判断语言、运行时、框架、存储、构建和分发方式，只讨论这次交付真正需要决定的部分。

- **已有项目**先看实际入口、依赖清单与锁文件、支持的平台版本、CI 和发布方式。现有栈能满足要求就沿用。确有缺口时，先比较补一个库或适配层能否解决，再计算换栈涉及的数据迁移、旧接口兼容、发布和回退成本。
- **新项目**先列硬约束，例如宿主 API、最低系统版本、联网权限、数据存放位置和预算。筛出可行方案后，比较团队能否维护、依赖和许可证、安装与升级、运行费用、性能及[资源占用](resources.md)。优先选能通过验收且维护成本低的方案。比较当前版本支持情况时，查官方文档或维护记录。

| 交付对象 | 会影响选型的问题 | 可以怎样验证 |
| --- | --- | --- |
| CLI、桌面或移动应用 | 能否在目标系统安装？是否需要离线运行、调用系统能力？ | 在最低支持环境里安装产物，完成一次典型操作 |
| 插件、库或 SDK | 宿主允许什么接口和运行时版本？使用方怎样引入或升级？ | 在受支持的宿主或最小调用项目中加载发布形态的产物，调用一个公开入口 |
| 后端服务或数据任务 | 数据量、并发、持久化和恢复要求是什么？谁负责运行它？ | 用代表性数据跑一次请求或批处理，观察资源峰值以及中断后的恢复结果 |
| 系统软件或嵌入式项目 | 目标架构、工具链、内存和存储有哪些限制？ | 构建目标产物，在目标设备或注明范围的模拟器里走通关键路径 |
| 网站 | 内容何时变化？哪些交互可在浏览器完成？哪些操作需要服务端身份或数据？ | 在目标托管环境验证一条从打开页面到完成任务的路径 |

已有证据足够时直接决定。仍有会改变选型的疑点时，用代表性场景做一次小验证。在已有任务单、PR 或设计记录里简要写下所选方案、决定性理由、尚待验证的条件，以及什么变化值得重选。需要新增持续费用、改变数据可见范围或大规模迁移时，按[决策指南](planning-and-decisions.md)确认相应取舍。

### 只引用本工作流时，怎样选用现成方法

看到“帮这个项目选技术栈”时，先判断还有哪个问题没有答案，再用下面对应的方法。当前客户端已提供合适的技能就按需使用；只有本工作流时，直接按这里的步骤完成。能沿用现有栈的小改动可以跳过比较表和原型。

- **两个方案都满足硬约束，怎样取舍？** 借用 Alireza Rezvani 的 `tech-stack-evaluator`。把沿用现有栈也列作候选，用同一份工作负载比较对结果影响最大的几项，例如迁移与回退的工时、同一周期内的运行费用、升级由谁负责。为每项写出依据或估算前提；确有取舍时再按项目优先级加权，看看调整关键假设会不会改变结论。上游比较脚本会给缺失的指标默认记 50 分。交付给维护者时把缺证据的项标为“待验证”，若它能改变选择，先补证据。[选型技能](https://github.com/alirezarezvani/claude-skills/blob/f8593c4941210a621a6629ce1da9e07897976d5f/engineering-team/skills/tech-stack-evaluator/SKILL.md) · [评分实现](https://github.com/alirezarezvani/claude-skills/blob/f8593c4941210a621a6629ce1da9e07897976d5f/engineering-team/skills/tech-stack-evaluator/scripts/stack_comparator.py)
- **争议在状态逻辑或交互上，怎样让人试出来？** 借用 Matt Pocock 的 `prototype`。先写下一条能区分候选方案的问题，给出一组输入和预期结果，只实现足够观察这件事的状态或操作。例如，用一个可操作的小样让维护者走完“暂停、取消、重新开始”，检查每一步允许哪些操作。遇到启动时间、内存、宿主兼容性等问题，就在目标运行时做最小验证，把实测结果写回原任务。[原型技能](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/prototype/SKILL.md)

例如，给离线 CLI 选择存储时，现有单文件格式和嵌入式数据库都可能可行。如果决定因素是“写入中断后能恢复上一批数据”，就先用同一组样本分别中断写入、重启、读回并核对记录。把恢复结果、安装产物增加了多少、迁移旧数据需要哪些步骤放在一起，再做决定。这样接手的人既知道选了什么，也知道在数据规模或恢复要求变化时该重测哪一步。

## 选择分支和工作区

先读接收仓库的贡献说明和近期合并的 PR，确认目标仓库、基分支、命名惯例和 fork 的推送位置。查看当前分支、未提交改动、已有工作树和相关 PR。如果已有任务分支或开放的 PR 与本次目标、基分支和授权范围一致，继续使用它，保留已有评审上下文。

需要新分支时，从确认过的最新目标基线创建，让一个分支对应一项可独立评审的改动。项目未规定格式时，可用简短、描述实际变化的名称，例如 `feat/export-csv`、`fix/retry-timeout`、`docs/offline-install`。优先使用适合的现有检出。并行工作或已有未提交改动确需隔离时，再使用单独的工作树。

分支名描述这次交付。Codex、Claude、其他 agent 和人工贡献都先看目标项目的约定；工具身份本身不决定前缀。仓库或宿主明确要求命名空间时，在其中保留有意义的任务名，例如 `codex/fix-import-path`。也可按项目习惯使用议题编号或短横线，例如 `142-fix-import-path`。已有合适分支继续使用。

合并前对高影响改动做[独立审查与交叉核验](independent-review.md)。报告的疑点要核对到实际代码、前提与证据，再决定修复、继续查证或驳回。

## 合并后清理任务分支

1. **核对合并证据。** 更新目标基分支的信息，分别读取本地分支和远端源分支当前的完整提交哈希。普通合并可用 `git merge-base --is-ancestor <tip> <base>` 核验该提交已进入目标基线。Squash 或 rebase 合并会改变提交身份，此时核对同一源仓库、源分支、目标仓库和基分支的已合并 PR，将待清理分支的 tip 与 PR **合并时**的 head 哈希比对，并确认合并结果已进入目标基线。若分支后来又有提交，保留它。[GitHub 合并方式](https://docs.github.com/en/pull-requests/reference/pull-request-merges)
2. **确认谁还在用。** 检查 `git worktree list`、关联工作树的未提交或未跟踪文件，以及以此分支为源或基线的开放 PR，包括堆叠 PR。常规清理只处理本任务独占的短期分支。保留受保护、默认、长期发布、共享、他人 fork 中的分支，以及仍有消费者或归属不明的分支。
3. **分别处理本地与远端。** 按已获授权的范围逐个处理，删除前重读对应引用。若有并发写入可能，使用能在提交哈希改变时拒绝删除的操作，缺少这种保障就保留分支。本地使用普通删除，遇到拒绝时保留并说明原因。远端已自动删除时，直接核对该引用已消失。分别回读两端状态，勿用强制操作绕过拒绝。`git branch -d` 检查的是跟踪分支或 `HEAD`，目标基线仍须单独核验。[Git 分支文档](https://git-scm.com/docs/git-branch)

分支引用、工作树和构建产物应分别检查。处理任务临时目录、进程和磁盘空间时，见[资源与收尾](resources.md)。需要报告实际腾出的空间时，在相同卷上比较清理前后的可用空间，并注明同期其他任务可能造成的变化。
