# 复用现有实现与管理任务分支

## 先找已有能力

1. 从用户实际调用的入口查起。搜索仓库已有功能、配置、脚本、测试、开放中的 PR，以及维护者近期合并的同类改动。确认现有实现能否直接满足需求，进行中的贡献能否接着做。一个配置项就能解决的问题，到这里即可结束查找。
2. 仓库内仍有缺口时，核对标准库、当前锁定版本的依赖和平台原生能力。需要新依赖时，再查官方文档、上游实现和仍在维护的同类项目。用任务里的一个实际输入或使用场景核验关键行为，检查版本兼容、维护状态、许可证和署名义务、所需权限、安全更新，以及引入和升级的成本。
3. 已有接口满足要求就直接采用。接口或数据格式有小差异时，用薄适配层衔接。只有现有方案有具体缺口时才自行实现，并只实现缺失的部分。影响依赖、兼容性或长期维护的选择，在现有 PR 或设计记录中用一两句写明比较过的方案、缺口和取舍。

工作方法也可复用。项目采用 GitHub Flow 时，沿用其分支与 PR 流程。已经使用 Superpowers 的项目可调用与当前任务匹配的技能，无需在仓库内复制整套流程。[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) · [Superpowers](https://github.com/obra/superpowers)

## 选择分支和工作区

先读接收仓库的贡献说明和近期合并的 PR，确认目标仓库、基分支、命名惯例和 fork 的推送位置。查看当前分支、未提交改动、已有工作树和相关 PR。如果已有任务分支或开放的 PR 与本次目标、基分支和授权范围一致，继续使用它，保留已有评审上下文。

需要新分支时，从确认过的最新目标基线创建，让一个分支对应一项可独立评审的改动。项目未规定格式时，可用简短、描述实际变化的名称，例如 `feat/export-csv`、`fix/retry-timeout`、`docs/offline-install`。优先使用适合的现有检出。并行工作或已有未提交改动确需隔离时，再使用单独的工作树。

## 合并后清理任务分支

1. **核对合并证据。** 更新目标基分支的信息，分别读取本地分支和远端源分支当前的完整提交哈希。普通合并可用 `git merge-base --is-ancestor <tip> <base>` 核验该提交已进入目标基线。Squash 或 rebase 合并会改变提交身份，此时核对同一源仓库、源分支、目标仓库和基分支的已合并 PR，将待清理分支的 tip 与 PR **合并时**的 head 哈希比对，并确认合并结果已进入目标基线。若分支后来又有提交，保留它。[GitHub 合并方式](https://docs.github.com/en/pull-requests/reference/pull-request-merges)
2. **确认谁还在用。** 检查 `git worktree list`、关联工作树的未提交或未跟踪文件，以及以此分支为源或基线的开放 PR，包括堆叠 PR。常规清理只处理本任务独占的短期分支。保留受保护、默认、长期发布、共享、他人 fork 中的分支，以及仍有消费者或归属不明的分支。
3. **分别处理本地与远端。** 按已获授权的范围逐个处理，删除前重读对应引用。若有并发写入可能，使用能在提交哈希改变时拒绝删除的操作，缺少这种保障就保留分支。本地使用普通删除，遇到拒绝时保留并说明原因。远端已自动删除时，直接核对该引用已消失。分别回读两端状态，勿用强制操作绕过拒绝。`git branch -d` 检查的是跟踪分支或 `HEAD`，目标基线仍须单独核验。[Git 分支文档](https://git-scm.com/docs/git-branch)

分支引用、工作树和构建产物应分别检查。处理任务临时目录、进程和磁盘空间时，见[资源与收尾](resources.md)。需要报告实际腾出的空间时，在相同卷上比较清理前后的可用空间，并注明同期其他任务可能造成的变化。
