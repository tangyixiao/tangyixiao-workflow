# 验收项目交付和扩展更新

## 动手前写清怎样算完成

从实际使用者的一次操作写起：“在〈目标版本、设备或客户端〉，从〈入口〉输入／操作〈代表性场景〉，应当看到〈可观察结果〉，用〈检查方法〉核对。”在现有任务或 PR 里记一行即可。涉及权限、已有数据或兼容性时，加一条最容易出错、且会改变是否可交付的场景。先查仓库、样例和已定范围；只有不同答案会改变交付结果时才请人决定。[需求与决策](planning-and-decisions.md)

完成后逐项记下实际版本、观察结果和证据。未执行的项目写明原因；失败的项目写出现象与接下来的处理。比如修复“关闭录像后仍在播放”，验收是打开录像、关闭播放器、等待并再读进度，随后重开能继续播放。代码已经合并、CI 通过、网站已部署、正式站复测通过，各自对应不同的证据。[发布范围](release.md#scope-a-release-update)

## 更新 Skill、插件或同类扩展

1. **定位实际使用的那份。** 查维护源、现有版本或提交、目标版本、客户端／宿主、配置档和安装位置。先看已有更新方式、兼容范围、变更说明、新权限和本地修改。如果同名扩展有几个副本，核对宿主实际加载路径。保留原版本、配置及恢复途径。
2. **更新到约定范围。** 用宿主支持的安装器或包管理器；支持预览时先读差异。自有扩展在维护源修改，再更新已约定的安装目标。保留本地定制、其他扩展、账号和项目设置。只有需要向外分发的任务才涉及发版或市场上架。
3. **用原入口验收。** Skill 更新后，在能重新发现它的新会话里试一次能区分新旧行为的任务；默认调用的验收用不带技能名的自然请求。插件更新后，在实际使用的宿主和配置档里核对启用状态，走一遍更新影响的操作。Desktop 和 Web 都在范围内时分别检查。遇到回归时，停止扩大更新，使用已核对的原版本和宿主恢复机制，再复测旧入口；数据迁移若不可逆，先核对恢复条件。

## 更新 Tangyixiao Workflow 自身

从选定的源码修订运行自检，再用**源码检出**中的 CLI 更新已知的 Skill 目录。在源码根目录运行下列命令，将 `DEST` 换为当前客户端实际使用的路径：

```text
npm run check
node bin/pwf.mjs install --destination "DEST" --json
node bin/pwf.mjs install --destination "DEST" --apply --json
node bin/pwf.mjs status --destination "DEST" --json
```

预览时逐项核对路径、变更和冲突，确认属于本次更新才执行 apply。检查 `status` 的安装状态，以及改动文件的哈希是否与预期源码一致。客户端重新发现后，按上一节实测新规则；分别记录已安装、已被调用和实际产出。项目侧的 `upgrade --project` 用来更新项目接入配置。普通任务默认使用已装版本；更新本 Skill 的一次任务到本次验收结束，避免每次调用都触发下载或再次自更新。
