# 怎么选名字

先说清给什么起名、谁会用、会在哪里看到或输入它。读一遍同一项目已有的产品名、术语、目录和调用示例。已经有准确且通行的叫法就沿用。日常变量、文件和分支可以直接按约定命名；只有会影响对外品牌、安装入口或兼容性的取舍才需要专门讨论。

## 把候选名放回使用场景

| 对象 | 怎么判断 |
| --- | --- |
| 产品、项目、插件 | 把名字放进 README 首句、插件市场条目和一次口头推荐里。看目标读者能否读出来、记住、搜到，并与相近产品区分。已有品牌沿用正式拼写；需要双语时区分固定品牌名和可本地化的功能描述。 |
| 仓库、包、命令 | 分开写展示名、仓库路径、含作用域的包名、可执行命令。按实际托管平台和注册表核对命名规则、同名和近似项；在支持的系统上检查命令是否会遮住已有命令。把候选放进一条真实形态的安装或调用示例，看人能否准确输入。 |
| 功能、菜单、文档 | 采用使用者对任务的叫法。拿相邻操作一起比较，尤其是“检查 / 修复”“停用 / 删除”这类结果差异大的词。让按钮文字准确预告点击后的结果。 |
| 模块、API、配置项、文件和代码符号 | 沿用该语言及仓库的词汇、大小写和层级。对照实际调用点、返回值、副作用和同级对象。名称应让维护者看出读写、单位或作用域等会影响使用的区别。分支名沿用[开发指南](development.md#选择分支和工作区)。 |

对一个新项目需要比较方案时，给出少量方向确实不同的候选，每个写一句它突出的特点和最容易被误解的地方，再推荐一个并说明理由。查重只查拟使用的渠道，记下查了哪里、何时查、发现什么；没查到重名只说明这次查询结果。公开发布前再核对最终名称，不因提出候选就注册、占用或改名。

## 一个例子

假设一个 CLI 只检查本地数据能否发版。在命令行帮助中并排读 `tool release` 和 `tool check-release`：前者容易让人以为会发布，后者直接说明只做检查。如果仓库已有 `notes-check`、`config-check` 这组命令，则推荐 `tool release-check`，同时保留动作含义和已有词序。这个理由比“听起来更专业”更容易检验。

## 改名和复用

已对外使用的标识先查引用者：安装命令、导入路径、配置键、文档链接、自动化和已有数据。如果只是调整界面叫法，优先保留机器读取的标识；确需更换时，给出新旧映射、别名或迁移方式，验证旧入口和新入口的预期行为。发行标题、标签与历史产品归属沿用[发布指南](release.md)。

只引用本工作流即可。若争议是“两个词是否指同一个概念”，可用 Matt Pocock 的 `domain-modeling` 对照真实场景和反例确定边界；若是变量、函数或类的叫法含糊，可用 Softaworks 的 `naming-analyzer` 对照调用点和仓库约定提出替代名。两种技能都可选，简单命名直接按上述方法完成。[domain-modeling](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/domain-modeling/SKILL.md) · [naming-analyzer](https://github.com/softaworks/agent-toolkit/blob/3027f20f3181758385a1bb8c022d4041dfb4de84/skills/naming-analyzer/SKILL.md)
