# 仓库交付与维护

先确定接收仓库、实际默认分支、这次改动影响谁，以及合并、发布、部署分别由谁负责。使用现有 PR、Issue 或发布记录记下必要结论。普通改动可在一两句话内交代。此流程也适用于向他人项目贡献。

## 每次收尾时过一遍的入口

逐项判断改动有没有让现有内容过期。需要更新的，在授权范围内更新并回读。可交给另一位维护者的，注明触发条件与负责人。未启用、不适用或本次无变化的，简要标明即可。检查入口本身不触发发布。

| 入口 | 什么时候需要更新 | 怎么证明确实生效 |
| --- | --- | --- |
| README / About | 项目定位、支持平台、安装命令、首次使用或主页地址有变 | 打开正确分支的渲染页面，跟随链接或验证一个关键示例。About 在仓库首页单独回读 |
| 默认分支 | 核对 PR 目标、当前提交及合并状态。堆叠 PR 要追到真正的默认分支 | 已合并才在目标分支读取对应文件或合并提交。开放 PR 给评审链接 |
| Release / 包 | 新版本、渠道、下载项、升级要求有变且已进入发布范围 | 回读 tag、Release、附件和实际分发渠道。草稿、已合并源码和可下载版本分别标明 |
| Discussions / Wiki | 有需要反馈的提案、值得告知订阅者的变化、反复出现的问题或过时的操作指南 | 优先更新现有讨论、FAQ 或权威文档。需要发帖时核对分类和可见页面 |
| Pages / website | 页面承诺、下载入口、多语言内容、域名或子路径受影响 | 先核对站点源码和构建结果，再按实际部署验证线上 URL、关键深链与下载。区分本地、PR 预览和正式站 |
| Actions / 其他入口 | 构建、安装、贡献路径或支持渠道受影响 | 查看本次提交对应的检查结果、失败摘要和必要的实际入口 |

例：修正文档中的一个安装参数，检查 README 和网站是否都引用该命令，记录 PR 的目标分支。若发版资产与讨论内容无变化，就结束这两项检查。

## 谁负责、谁有权决定

从项目的贡献指南、维护者名单、文件负责人和发布流程里找依据。对涉及多人或跨仓的动作，写清提出改动的人、评审人、拥有最终决定权的人，以及发布后处理故障的人。一个人可以承担多个角色。缺少依据的身份写“待确认”。

- 外部贡献者可在授权范围内准备分支、PR 和说明。由上游维护者决定是否合并、何时发布，按实际角色署名。
- 文件评审、受保护分支合并、签名发包、市场收录和网站部署可能分别由不同人或服务负责。可写权限表示技术能力，项目决定与本次操作范围仍须有依据。[GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
- 有人实际承接后再写维护承诺。交付待办写明负责人或接收入口、下次检查的触发事件、版本停更或交接方式。

## 让合适的人找到并用起来

按项目受众维护一句有辨识度的 About、相关 topics、能访问的正式入口、可操作的 README 和确有用处的演示。发布、征求反馈或申请收录时，选择相关社区允许的渠道，遵守署名和推广规则；代表项目对外发帖需要相应授权。[GitHub topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)

用已有访问来源、下载、安装失败反馈、重复问题来判断优先修哪一个入口。维护范围随项目规模调整。主要版本发布、平台升级、链接失效或重复工单可作为复查时点。只有实际需要时增加定时任务；同一变更合并为一条公告。衡量效果优先看读者能否成功找到、安装和使用项目。
