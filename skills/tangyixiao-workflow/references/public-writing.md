# 公开协作写作

在自己的仓库和向其他项目贡献时，都从接收项目开始。先读适用的 `CONTRIBUTING`、提交说明和对应模板，再看维护者近期接受的同类条目。遵守项目指定的语言、标题格式、必填字段、署名和发布渠道。项目留白处可采用下面的默认写法。一次投稿只需准备相应的内容，无需向仓库添加模板、标签、机器人或本工作流的标识。

## 从起草到交付

1. **确定对象和目的。** 确认仓库、分支或版本，找到对应的模板和已有讨论。想清楚读者读完要做什么，例如复现故障、评审取舍、升级软件或运行第一个示例。
2. **根据事实起草。** 从差异、复现记录、版本产物或可公开引用的决定提取事实。标题点明对象和变化、故障或待答的问题。首段先写对读者的影响，再补理解它需要的背景。简短事实用一两句话即可。
3. **核对证据和呈现。** 逐条核对范围、数字、命令、链接与归属。写测试结果时注明实际运行的检查和条件。区分本地通过、CI 通过、已合并、已发布和实际运行，各自对应具体证据。预览目标平台的 Markdown，检查列表、代码块、图片、相对链接和锚点。移除占位文字、任务聊天、私有路径与凭据。
4. **按授权交付。** 草稿交付可直接给出完整标题和正文。提交、推送、发帖、合并、发布各按已有授权执行。发布前再次核对目标、可见性和最终正文，注意 `Closes` 等关键词可能改变关联事项的状态。
5. **发布后回读。** 打开实际页面或读取已保存的对象，核对标题、正文、目标版本和相关链接。图片、折叠块等依赖渲染的内容，另看页面效果。交付时给出实际链接或提交哈希，并如实写明仍待完成的环节。

## 按载体取舍

下表方括号里的文字表示需填入的事实。沿用项目现有标题习惯，只保留读者用得上的内容。

| 载体 | 标题写法 | 正文重点 |
| --- | --- | --- |
| Pull Request | `[动作] + [受影响对象]` | 说明要解决的问题、评审者可观察到的变化，以及怎样核验。涉及兼容性、迁移或设计取舍时，说明原因和影响。纯文档 PR 可直接写哪条说明变了、核对了什么。关联确有关系的议题。 |
| Commit | `[动词] + [单一改动]` | 标题让人能在历史中找到这次改动。差异难以看出原因时补正文，说明约束或行为变化。前缀、签署和共同作者行按仓库规则和实际贡献填写。 |
| Issue | 缺陷用 `[触发条件] 下 [观察到的现象]`，建议用 `[场景] 需要 [能力]` | 缺陷写环境或版本、最短复现步骤、期望与实际结果，附必要且脱敏的日志。建议说明使用场景、现有困难和可验收的结果。原因尚待确认时明确标作推测。 |
| Discussion | 用一句可回答的问题，或写明需要讨论的选择 | 交代背景、已知约束、尝试过的做法，最后指出希望谁就什么问题给出意见。已有共识时链接原讨论或决定。 |
| Release | 沿用项目的产品名、版本和预发布标记习惯 | 先写本版对使用者的影响，再写获取或升级方法、兼容性和已知限制。下载项、校验值、渠道状态均对照该版本产物。项目已经选用固定发布格式时，沿用其栏目和顺序。详见[发布规范](release.md)。 |
| README | 实际项目名，开头一句说明谁可用它做什么 | 按首次使用顺序给出前提、快速开始、一个真实示例及可观察的结果，再链接帮助入口和适用许可证。纯文档或资源仓库可用阅读入口、查找路径和真实条目作为快速开始与示例。帮助和许可信息取自本仓库的实际记录。详见[文档规范](documentation.md)。 |
| GitHub About | 用一句话描述项目当前能完成的具体任务 | 主页字段指向有效的项目入口，topics 选与功能、技术或用途直接相关的关键词。打开仓库首页，核对实际展示的简介、链接和 topics。 |
| Wiki | 用读者要完成的任务命名页面 | 首页按使用任务组织，正文给出适用版本、前提、步骤和可观察的结果。与仓库里的版本文档共用事实来源，涉及不同版本时链接对应文档。检查已发布页面、导航和页面间链接。 |
| GitHub Actions | 工作流名写用途，作业名写检查对象，步骤名写具体动作 | 运行摘要（run summary）写明检查或构建了什么、结果如何。失败时指出具体作业和步骤，给出日志位置和可执行的下一步。保持分支保护所依赖的必需检查名称稳定。重复运行时尽量更新已有自动评论，只在结果变化或需要人工处理时通知。 |

遇到表格以外的公开入口，同样先确认读者和用途，再选择最短的有效形式。评审评论指明相关代码或段落，写出触发条件、具体影响和希望作者确认或修改的事项。Changelog 按项目约定归入对应版本，描述使用者能感知的变化。迁移指南和其他文档围绕读者的一项任务写清适用版本、操作和结果。需要进一步核验时，在相应位置链接公开依据。

## 读者、身份与示例

软件用户、管理员、账号所有者是产品里的角色，可以直接写，例如“只有仓库管理员可以修改此设置”。避免把协作对话写进产品说明。假设差异只补充了 README 里的依赖说明，PR 标题可写“在快速开始中列出构建依赖”，正文说明新增哪项依赖、在哪一步需要它。评审者由此能直接对照差异。“按用户要求完善文档”略去了实际改动。

贡献署名、决定出处、许可证或致谢需要指明身份时，沿用真实作者或项目认可的称呼。有公开依据且确由 Tangyixiao 作出的决定才归于 Tangyixiao。外部项目沿用其自身的维护者、品牌和致谢方式。示例中的链接、测试数量、版本、截图和维护者认可都应能追溯到本次工作的材料。

## 公开标注 AI 贡献

Codex、Claude 和其他助手遵循同一约定。默认按项目现有身份工作。助手实际完成了可说明的贡献（例如实现功能或编写测试），且署名能准确表达这项贡献时，可以主动提议。答疑、查资料、例行检查通常无需发起署名请求。

提议时说清 **做了什么、准备写的准确文字或账号、写在哪里、适用哪几次提交或哪份文档**。例如：“这次 Claude 编写了导入器的回归测试。我建议在这个 PR 的致谢段加一句『导入器回归测试由 Claude 协助编写』，只用于这一个 PR。可以吗？”若提议使用提交作者身份或 `Co-authored-by`，应展示完整作者行和可核实的身份，并说明 GitHub 可能据此显示贡献者。PR 或 README 的文字致谢与提交署名分别确认。

Git 有三个独立的署名位置：主作者（`Author`）记录谁创作了这次改动，提交者（`Committer`）记录谁创建了这个提交对象，联合作者记录在消息末尾的 `Co-authored-by`。**只要其中任何一处将使用 AI 助手身份，包括工具自动填入的身份，都要在创建提交前先征得明确同意。** 一次请求可以列出多个角色，须列明各角色的姓名和邮箱、实际贡献及涉及的提交。同意某个角色只覆盖该角色。导入已有源码时，应区分原作与导入操作。

收到明确同意后只按约定范围添加。没有答复或对方拒绝时，省略可选的 AI 署名并继续原任务。要求使用某工具、提交、合并、发布，或此前同意给另一个助手署名，都不自动授权这次署名；已有批准明确涵盖同一助手、仓库、载体和范围时，直接沿用。

创建提交前用 `git var GIT_AUTHOR_IDENT` 和 `git var GIT_COMMITTER_IDENT` 核对有效身份，同时检查命令行覆盖、联合作者尾注、PR 模板及客户端自动追加的页脚，尤其是 squash 后的最终消息。可选的自荐文字须先获准；若平台操作必然公开 AI 账号或上游要求披露，提前说明并确认本次公开方式，再执行该动作。保留真实的平台操作身份、已有贡献者和签署记录。提交后用 `git show -s --format=fuller <sha>` 核对两个身份和尾注；合并或 squash 后回读目标分支的最终提交，公开致谢则回读实际页面。

## 自动化提交的联合署名

在 Tangyixiao 的项目中，所有以 bot 身份写入仓库的 Git 提交都要保留 bot 为主作者，并使用下面这行联合署名。规则按提交行为适用，覆盖 Dependabot、Renovate、GitHub Apps、AI 编码 bot，以及通过 CI、定时任务或本地脚本提交的自动化。依赖升级、同步数据、更新文档、格式化代码和发版回写都适用。

```text
Co-authored-by: Tang Yixiao <115929632+tangyixiao@users.noreply.github.com>
```

在创建提交的位置设置 commit message，正文后空一行，再写 Git trailer。每位联合作者只列一次，保留已有签署行和其他贡献者。提交到其他人维护的仓库时，遵循接收项目的规则，按实际贡献署名。

能配置 bot 提交消息时，在源头为每个提交添加署名。如果托管 bot 的原始提交消息不可配置，且项目允许 squash 合并，可在最终提交消息补齐署名，核实主作者仍是该 bot。核验记录应写清覆盖的是原始提交还是 squash 后落到目标分支的提交。对于只发评论、打标签或运行检查且没有创建提交的 bot，无需额外制造提交。

Dependabot 的依赖更新可参考本仓库 PR #3：合并时使用 squash，最终提交的主作者是 `dependabot[bot]`，末尾保留了 bot 的 `Signed-off-by` 和 Tang Yixiao 的 `Co-authored-by`。准备 squash 时核对最终消息，避免合并工具丢掉署名。[PR #3 的最终提交](https://github.com/tangyixiao/tangyixiao-workflow/commit/13ed33d6d84d30180840f14e7e900c1ea2c7e1b1)

推送或合并后，从目标分支取本次实际保留的每个 bot 提交 SHA，用 `git show -s --format="%an <%ae>" <sha>` 核对主作者，再用 `git show -s --format=%B <sha> | git interpret-trailers --parse` 检查上述署名是否恰好出现一次。[GitHub 联合署名说明](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors)
